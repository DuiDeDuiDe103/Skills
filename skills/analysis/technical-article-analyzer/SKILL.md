# 技术文章架构分析

## 输入处理

接受以下输入：

- 本地 TXT 或 Markdown 附件
- Codex 附件中的 `pasted-text.txt`
- 用户直接粘贴的长文本
- 网页文章链接
- 文章内容和项目代码库
- 当前消息带有文章附件，但用户只说“这个呢”“这篇干嘛”

按以下优先级取得正文：

1. 优先读取用户提供的本地附件或粘贴文本。
2. 只有缺少正文时才打开网页链接。
3. 从头到尾完整阅读正文后再分析；长文要继续读取到末尾，不能只根据标题、摘要或局部片段推测。
4. 无法取得完整正文时，明确说明已读取的范围和限制，不把局部判断包装成全文结论。
5. 用户同时提供多个版本时，确认分析对象；上下文已足够明确时不要重复询问。

## 选择输出深度

根据用户当前问题选择最小充分深度，不要所有文章都输出同样长度。

### 精简模式

当用户只问“这篇干嘛”“这个呢”“作用是什么”时，回答：

1. 核心问题
2. 系统定位
3. 主执行流程
4. 最重要的学习目标
5. 一个必要的风险提醒

保持紧凑，不自动展开所有类、代码和边界。

### 详细模式

当用户问“有哪些细节”“深入分析”或要求评审方案时，按文章实际内容展开：

- 完整执行流程
- 核心类、数据结构和状态变化
- 关键设计原因
- 边界情况
- 并发、容错、性能、安全和一致性
- 风险、缺陷与改进建议
- 必要的源码验证

### 定点模式

当用户只问文章中的一个概念、类或判断时，只回答该问题。结合文章上下文解释来源和用途，但不要重新总结整篇文章。例如，询问 `McpSyncClient` 是否由 JDK 提供时，只说明其来源、项目用途和“同步”的含义。

## 分析工作流

### 1. 找出核心问题

先回答：

> 如果没有文章介绍的这个模块，系统会遇到什么问题？

用一句话说明模块为什么出现，不要只改写标题。

### 2. 确定系统定位

把模块放回端到端链路，说明：

- 上一步是什么
- 接收什么输入
- 输出什么
- 下一步交给谁
- 属于路由层、检索层、工具层、后处理层、Prompt 层或其他层

优先使用简短箭头流程，并用 `← 本文` 标出文章焦点：

```text
意图识别
→ 选择工具
→ 参数提取 ← 本文
→ 参数校验
→ 执行 MCP 工具
→ 格式化结果
→ LLM 生成答案
```

只有复杂分支、并发路径或状态变化明显时才使用 Mermaid。

### 3. 提炼主执行流程

把代码和说明归纳为可记忆的执行链路：

- 不照抄文章。
- 保留关键数据结构和状态变化。
- 明确每一步的输入、处理和输出。
- 区分主路径、失败路径与降级路径。
- 简单流程使用箭头；图能显著降低理解成本时才画图。

### 4. 解释关键设计选择

针对重要选择说明“为什么这样做”以及解决了什么工程问题，例如：

- LLM 与规则的选择
- 单线程池与多线程池
- 去重与精排的先后顺序
- 定向检索与全局检索
- 注册表、默认值、白名单与 Schema
- 降级、超时、重试和异常隔离

不要停留在“代码做了什么”；说明约束、收益和代价。文章没有给出理由时，标记为推断。

### 5. 提炼实现细节

只选择文章真正涉及且与用户问题相关的维度：

- 核心类、职责和方法调用关系
- 关键数据结构和输入输出对象
- 配置项、阈值和默认值
- 并发模型、线程池和共享状态
- 超时、重试、降级与异常处理
- 缓存和数据一致性
- Prompt、JSON 与 Schema 解析
- 权限、租户隔离与数据安全
- 日志、指标和链路追踪
- 扩展性、设计模式、性能与资源成本

不要为了凑齐栏目而展开文章未涉及的内容。文章未说明但生产环境通常需要的能力，可以作为“缺失项”指出，不能虚构其实现。

### 6. 检查隐藏问题

不要默认接受文章的所有结论。主动检查：

- 文字描述与展示代码是否一致
- 所谓并行是否实际串行或被阻塞等待抵消
- 异常被捕获后是否把失败统计成成功
- 是否缺少超时、取消、重试上限或资源回收
- 共享可变对象是否存在线程安全问题
- 默认值降级是否被误当成安全方案
- 是否缺少 Schema、类型、枚举、白名单或权限校验
- 是否可能越权检索、跨租户访问或泄露数据
- 是否存在请求、线程、Token、内存或下游调用放大
- 是否把 LLM 输出直接当成可信输入
- 方案是否只适合 Demo 而不适合生产

始终区分：

- **文章事实**：正文或展示代码明确表达的内容
- **源码事实**：当前项目代码库实际验证的内容
- **合理推断**：根据代码和工程常识推导、尚未证实的判断

不能把推断描述成已证实事实。证据不足时直接说明。

### 7. 必要时验证项目源码

仅当用户提供或指定代码库，并且问题需要核实文章引用的类、方法或实现时：

1. 优先使用可用的代码索引或 CodeGraph 定位符号和调用链；没有索引时再使用本地搜索。
2. 检查文章代码与当前代码库是否一致。
3. 链接实际文件和关键行。
4. 明确版本差异、已删除实现或文章片段的上下文缺失。
5. 不要仅凭文章代码判断当前项目实现。

用户只要求文章概述时，不进行大范围代码库搜索。

### 8. 给出最终记忆点

用一句便于复习的话收束核心设计，例如：

> 意图识别决定调用哪个工具，参数提取决定传什么，Schema 校验决定这次调用能否安全执行。

## 默认输出

精简模式优先使用：

```markdown
这篇文章解决的是：

> 一句话概括核心问题。

它在系统中的位置是：

流程箭头

主要完成：

1. ...
2. ...
3. ...

真正要学会的是：

> 一句话说明设计思想。

需要注意：

- 最关键的限制或风险。
```

详细模式可使用：

1. 核心问题
2. 系统定位
3. 完整执行流程
4. 核心类与数据结构
5. 关键设计原因
6. 并发、容错与性能
7. 安全与一致性
8. 文章或代码中的潜在问题
9. 最终记忆点

根据文章内容删减空栏目，不机械套模板。

## 表达规则

- 使用中文，先给结论，再解释原因。
- 保持系统架构视角，术语首次出现时简要解释。
- 简单问题简短回答，复杂问题才深入拆解。
- 减少教学仪式和重复，不强制出题或询问“懂了吗”。
- 不照抄大段原文，不虚构类、配置、数据或运行结果。
- 不使用“显然”“很简单”“你应该知道”等表达。
- 具体判断尽量贴近对应证据；涉及网页或代码库时提供可点击来源。
- 用户的明确关注点高于默认输出结构。
